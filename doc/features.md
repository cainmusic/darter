# Darter 特色功能

Darter 不是「把 diff 丢给 AI 改一遍」的一次性工具，而是一条**从 review 报告到可合并归档分支的完整闭环流水线**。下面按「它凭什么比裸调 claude 更靠谱」来梳理它的特色。

---

## 1. 端到端闭环自动化

喂入一份 code review 报告 + 一个 git 仓库 + 项目约束，剩下的全自动：

```
报告拆解 → 修复循环 → 宏观回归 → 人工审查 → 归档 → 最终审查 → 交付
```

- **拆解**：`ParseReport` 把报告拆成独立任务，`ReviewTasks` 再质检（查漏 / 去重 / 粒度 / **冲突合并**——多个任务改同一文件时合并或排序，避免互相覆盖）。
- 每个环节都有状态机、可续跑、可回滚，不是「一把梭」。

## 2. 多重对抗性审查（每任务三道关）

每个修复任务在提交前必须连过三关：

1. **语法/编译自检**（`syntaxcheck`）——硬性校验，不依赖模型判断，Go/Python/JS/Shell 都有对应检查。
2. **对抗性审查**（`Review`）——AI 扮演挑剔审查员，**读全文件 + 全库 Grep 调用点**核实，专挑残留缺陷、新引入问题、破坏下游的改动，而不是只瞟一眼 diff。
3. **提交范围检查**（`CheckCommitScope`）——确认 diff 没混入与当前任务无关的改动（别的文件、调试代码、无关重构）。

任务级之外，整体还有**宏观回归审查 → 人工审查 → 归档回归审查 → 人工确认**四层把关。

## 3. 反馈闭环自愈

审查不通过不是「报个错就停」，而是**把审查结论 + 上一轮 diff 原样喂回 AI**，让它先判断意见是否成立：

- 成立 → 据此修正；
- 不成立 → 说明理由、保留正确改法。

自检失败、提交污染同理回炉。最多 `max_retries` 次，形成真正的「修复 → 审查 → 反馈 → 再修复」闭环，而不是一次性重试。

## 4. 本地 claude 驱动，零 API key 依赖

AI 引擎是**本地 `claude` CLI 子进程**，不碰云端 API、不需要 key：

- 模型在设置页配置（`opus`/`sonnet`/…），换模型零代码改动。
- prompt 走 **stdin** 而非命令行参数——审查器携带完整文件上下文后提示词可能很大，走 argv 会触发 `E2BIG`（argument list too long），走 stdin 无此限制。
- `Fix` 用 `acceptEdits` 允许自动改文件；审查类调用关闭授权，避免误操作。

## 5. 归档 = 一任务一 commit（可追溯交付）

归档不是「把修复分支直接合并」，而是**从 base 分支重新逐个迁移已批准任务**，每个任务恰好一个 commit：

- **cherry-pick 优先**：忠实还原人工批准的内容，不重复审查。
- 真实冲突才降级为 `apply patch`，再不行才交 AI 重新实现（唯一产生「未经人工批准新内容」的路径，走完整审查链）。
- 每个 commit 正文带 `Task-Id:` trailer，配合 `git log -S` / `git blame` 可精确追溯到「哪个任务、哪次审查、哪个问题」。

最终交付物是一条干净、独立、每个改动都对应一个明确任务的归档分支，可直接 review / cherry-pick / 合并。

## 6. 归档卡点人工介入（不整单失败）

归档迁移某个任务受阻时，**不再把整个 job 判失败**，而是进入 `archive_blocked` 卡点，工作台弹交互区三选一：

- **让 AI 重试**（可附一句补充意见）；
- **我已手动改好，继续**（校验后直接提交人工改动，不跑 AI）；
- **放弃该任务**（记为遗留，不再归档）。

处理完自动续跑，其余已归档任务不受影响。

## 7. 最终审查自动闭环（修不掉的才报告）

归档迁移完做最终回归审查，发现问题时**先派无交互 AI 自动修**，而不是停下来等人：

- AI 修复改动 **amend 合入最后一个 commit**，不新增 commit，保住「一任务一 commit」的对应关系；
- 循环重试 `max_retries` 次，直到通过；
- 实在修不掉才停在 `fail`，展示报告，可重新归档再试。

始终有人工兜底，没有永久卡死点。

## 8. 诚实的遗留问题清单

宏观回归审查发现的问题，**不在归档阶段盲目乱修**（避免越修越乱、责任不清），而是固化成 `remaining_findings` 遗留清单交付，交人工判断跟进。归档阶段只保证两件硬事：**迁移出来的分支能编译** + **commit 与任务一一对应**。

## 9. 崩溃恢复 + 孤儿进程清理

- **窗口期崩溃恢复**：commit 已成功但状态未落盘时崩溃，重启后通过 commit 正文的 `Task-Id:` trailer 识别并回填哈希，不重复修复。
- **孤儿 claude 进程清理**：启动时清理遗留子进程，PID + 启动时间 + 命令行**三重校验**防止 PID 复用误杀无关进程。

## 10. 幂等续跑

修复循环、归档都能**随时中断、随时重来**：已完成的步骤自动跳过，只补跑剩余部分。配合 `paused`（执行完当前任务后暂停）/ `cancelled`（取消）状态，长任务也能放心打断。

## 11. 约束红线贯穿全程

项目约束（如「不得改公共 API」「遵循某编码规范」）会被注入到**每一次** AI 调用——修复、对抗审查、宏观回归、归档审查、最终审查。配合可复用的约束模板，保证 AI 每一步都守团队规矩。

## 12. 实时日志 + 历史回放

SSE 实时推送 + 进页面时回放历史事件，`claude` 子进程的 stderr 实时透传到前端日志，AI 在「想什么、在干什么」全程可见、可排查。

## 13. 单一二进制交付

前端（Vue3 + Naive UI）通过 `go:embed` 内嵌进后端，`make build` 一条命令打出一个二进制，部署零依赖、无前后端分离的运维负担。

## 14. 分支安全校验（防误操作）

同一个仓库会被多个 job 轮流使用，临时 fix/archive 分支容易残留。Darter 在每个入口做分支校验：

- **创建时**校验配置的 base 分支真实存在，分支名笔误立即报错；
- **拆解/预检**只在 base 分支上运行，「该问题是否已存在」的判断不被遗留临时分支污染；
- **开始修复/归档**校验仓库当前分支是否属于本 job（base / fix / archive），杜绝在别的任务遗留分支上误跑。

## 15. 人工兜底的控制面（归档冻结 + 全任务重做）

除正常归档外，提供两个「反悔」出口：

- **归档冻结**：不走归档迁移，一键把任务冻结为 `archived` 归档态——临时分支保留、工作区切回 base 并清空，适合「放弃本轮、留档冻结」。
- **全任务重做**：抛弃当前 fix 分支、基于 base 重建、保留任务列表、清空所有任务状态，从头再来一次修复循环。

## 代码迁移模块特色

代码迁移（migration）把「源分支的一批 commit 迁到目标分支」做成可控、可审查的流程：

1. **两栏 diff 精确对齐**：左源 commit、右目标 commit，用迁移时记录的 `target_commit` 精确对齐，不做 message 匹配（message 会被手动 amend 改掉）；reset / amend / merge 后状态判断仍精确。
2. **冲突 AI 解决 + 审查**：冲突走最多 3 轮「AI 解决 → 审查」，审查驳回则恢复冲突态重试。
3. **空 commit / 仅生成物自动跳过**：AI 结合项目约束判断「这个 commit 应跳过」（改动已在目标分支 / 全是生成物），直接 abort + 跳过，不提交空 commit；无冲突直接过的不管。
4. **全自动迁移**：按列表逐个 cherry-pick，冲突自动 AI 解决后继续直到完成，过程中周期性落盘、可中途停止、崩溃可恢复。
5. **全量回归审查**：迁移完成后对累积改动做完整性审查，发现问题走 3 轮「修复 → 审查」，修复单独成 commit（不混入迁移 commit），便于逐个评估合并去向。
6. **冲突解决详情留档**：每条冲突记录带 `target_commit` 精确关联「这次解决产生了哪个 commit」，避免 reset / merge 后反推出现「假冲突」。
7. **精细控制**：手动迁移、忽略（单条/区间）、合并（squash）、重置、改迁移目标、标记等，全程留档可续跑。

---

## 一句话总结

Darter 把「AI 改代码」这件单点的事，升级成了**可追溯、可续跑、可回滚、有人工兜底、有自动闭环**的任务工具集合——审查修复交付一条干净的归档分支，代码迁移交付一条按序迁移的目标分支，每处改动都能追溯到源头。
